## 1. Направления (по каждому — найди лучшие практики 2025–2026 у топов и примерь к «Начерту»)

1. **Данные пользователей и 152-ФЗ.** Что мы храним (пройди все таблицы `store.put`), где, сколько, кто видит; минимизация,
   сроки хранения и автоудаление, шифрование полей (envelope encryption, KMS Yandex Cloud), псевдонимизация в журналах,
   выгрузка/удаление «одной кнопкой», локализация данных в РФ, что уходит третьим лицам (ProxyAPI/Anthropic, Метрика,
   Telegram) и как это сократить.
2. **Вход и сессии.** Passkeys/WebAuthn (вход без пароля и кода), привязка сессии к устройству, ротация и отзыв сессий,
   обнаружение подозрительных входов, защита аккаунта владельца (админ) — отдельный фактор, короткие сессии.
3. **Защита фронта.** Строгая CSP (nonce/hash вместо `unsafe-inline`), Trusted Types, Subresource Integrity, изоляция
   сторонних скриптов (аналитика), заголовки безопасности (на GitHub Pages их не поставить — что делать: Cloudflare/Яндекс
   CDN перед сайтом?), защита от кликджекинга, Permissions-Policy.
4. **Цепочка поставок и секреты.** Зависимости `server/` и `node_modules`, закреплённые версии и хеши, Dependabot/OSV,
   подпись коммитов и артефактов (Sigstore), минимальные права токенов GitHub Actions (OIDC вместо долгоживущих ключей в
   Yandex Cloud — workload identity federation), разделение прав Штаба: агент не должен мочь выкатить в `main` без проверки.
5. **ИИ-безопасность.** Prompt injection (текст студента, фото листа, содержимое репозитория для Штаба), утечки системного
   промпта, злоупотребление бюджетом, «агент с правами записи»: песочницы, allowlist действий, человек в контуре, журнал.
   Что из лучших практик (OWASP LLM Top 10, guardrails, structured outputs, verifier-модели) у нас стоит добавить к сверщику.
6. **Надёжность «без отказов».** SLO и бюджет ошибок для API кабинета и наставника, health-checks и синтетические проверки
   прод-сайта по расписанию, алерты владельцу (Telegram), запасные модели и провайдеры, graceful degradation, резервные копии
   YDB и **учения по восстановлению**, идемпотентность записей, повторы с backoff, circuit breaker.
7. **Выкатка как у топов.** Feature flags, canary/процентная выкатка (развитие идеи `/new/`), мгновенный откат, preview-
   окружения на каждую ветку, миграции схемы без простоя.
8. **Наблюдаемость и стоимость.** Структурные логи, трассировка запроса (сайт → функция → модель), метрики стоимости на
   пользователя/фичу, автоостановка при перерасходе (ProxyAPI кончился 22.11 — как это ловить заранее), дашборд в пульте `me/`.
9. **Качество ядра — «математически без ошибок».** У нас уже мутационные проверки. Что ещё делают топы: property-based
   testing (fast-check), дифференциальное тестирование двух независимых реализаций, формальная проверка инвариантов
   геометрии, точная арифметика там, где важно, fuzzing парсеров (фото листа, ввод студента), регрессия по снимкам.
10. **Производительность и офлайн.** PWA уже есть (`sw.js`) — офлайн-режим для ДЗ, предзагрузка, Web Workers для тяжёлой
    геометрии (ИГ строит линии секундами), WASM, кэш на краю сети, бюджет производительности (Core Web Vitals) в проверке.
11. **Приватная аналитика.** Обезличенная аналитика без cookie, дифференциальная приватность для статистики режимов,
    k-анонимность в отчётах владельцу.

Если найдёшь важное направление вне списка — добавь, с обоснованием.

## 2. Как оценивать

По каждому механизму:

| Поле | Что написать |
|---|---|
| Что это | одной фразой, без жаргона; кто из топов так делает (компания, год, ссылка на первоисточник — инженерный блог, RFC, стандарт) |
| Что у нас сейчас | с `файл:строка`; «нет» — тоже ответ |
| Куда внедрить | конкретный файл/модуль/сервис |
| Плюс для «Начерта» | измеримо: какой риск закрывает, какой отказ предотвращает, сколько денег/времени экономит, что видит студент |
| Цена | ₽ в месяц (Yandex Cloud, сервисы), часы работы, новая зависимость или нет |
| Сложность и риск | что может сломаться; совместимо ли с «один `index.html` без сборки» и GitHub Pages |
| Приоритет | P0 (закрыть сейчас — реальная дыра), P1 (большой выигрыш, умеренная цена), P2 (красиво, но потом) |

Честность важнее красоты: если механизм топов нам не нужен (масштаб не тот, цена несоразмерна) — так и напиши, почему.
Не выдумывай уязвимости: каждую дыру подтверди путём в коде и сценарием атаки; непроверенное помечай «гипотеза».

## 3. Что сдать

1. **Резюме для владельца** — 10 строк простым языком: где мы сейчас («Лада» по каким пунктам, «Мерседес» по каким), три
   главные дыры, пять внедрений с наибольшей пользой на рубль.
2. **Таблица «что уже есть»** (раздел 0).
3. **Реестр рисков** — угроза → вероятность → ущерб → что закрывает (модель угроз STRIDE для: сайт, кабинет, наставник, Штаб,
   GitHub Actions, секреты).
4. **Каталог механизмов** по разделу 1 в формате раздела 2, отсортированный по приоритету.
5. **Дорожная карта** на 4 недели: по неделям, каждая задача — «что / где / готово, когда / как проверить», в стиле задач
   Штаба (`docs/HQ.md`), чтобы её можно было сразу отдать исполнителю. Всё новое — сначала в копию `/new/` и за флагом.
6. **Чего не делать** — модные решения, которые нам навредят или не окупятся.

Формат — один документ Markdown `docs/ENGINEERING-RESEARCH.md`, по-русски, без воды. Ссылки на первоисточники обязательны.
