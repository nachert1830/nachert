## 1. Цель и законы системы

Владелец только говорит, что нужно. Система сама понимает, кому и что поручить, делает, проверяет и выкатывает.
Цель этого задания — чтобы Штаб сам довёл до конца работу из 15–30 связанных задач (например, ИИ-ассистента на чертеже).

Законы — соблюдай в каждом решении:
1. **Деньги — по сложности.** Простое делают дешёвые модели. Opus — только: план эпика, разбор провала, задачи с пометкой
   «ядро». Цель: ≤ 20 % вызовов Opus от числа задач эпика.
2. **Тесты — судья.** Ни одна правка не попадает в main без зелёной проверки. Нельзя отключать, ослаблять, пропускать тесты,
   править `tests/baseline.json`, чтобы стало зелёным. Новая функция приходит со своей проверкой.
3. **Всё видно владельцу.** Каждый шаг — запись в ленте «Разговор» с кнопками. Каждый рубль посчитан.
4. **Решения владельца — только те, что его.** Утвердить план эпика, ответить на вопрос, где без него нельзя. Остальное — сама система.
5. **Безопасность.** Ключи никогда не попадают в вывод моделей, логи, комментарии. Монолог владельца — только в закрытой базе.
6. **Остановка лучше порчи.** Не уверен, бюджет кончился, два провала подряд — пауза и вопрос владельцу, а не попытка наугад.

## Часть A. Командная строка исполнителя (`tools/hq-agent.js`)

Новые команды для одиночного исполнителя, Архитектора бригады и режима сеанса (часть C):

```
RUN: команда        — выполнить команду в копии репозитория на машине Цеха (до 10 мин), ответ — код выхода и последние 8000 символов вывода
CI: номер_запуска   — конец лога упавших заданий запуска GitHub Actions (только чтение)
```

Правила RUN — реализуй строго:
1. Команда запускается через `bash -lc` в корне копии, `cwd` = корень, таймаут 10 мин, вывод обрезается до последних 8000 символов.
2. **Окружение дочернего процесса — без секретов**: удали из `env` всё, что содержит `KEY`, `TOKEN`, `SECRET`, `PASSWORD`, `GH_`, `GITHUB_TOKEN`
   (сравнение по имени, без учёта регистра). Тест обязателен: `RUN: printenv` не показывает ни одного такого имени.
3. Запрещено (проверка до запуска, регулярным выражением по всей строке команды; при совпадении — отказ с причиной, команда не выполняется):
   `git push`, `git remote`, `git config`, `gh `, `curl`, `wget`, `nc `, `ssh`, `scp`, `sudo`, `rm -rf /`, `rm -rf ~`, `npm publish`,
   `printenv`/`env` с выводом ключей (п. 2 и так их убирает), `/proc/*/environ`, `.github/workflows` (запись), `tests/baseline.json` (запись),
   перенаправление в файлы вне репозитория, кроме `/tmp`.
4. Разрешено всё остальное: `node`, `npm test`, `node tests/run.js --only=…`, `node --test …`, `ls`, `cat`, `head`, `tail`, `grep`, `find`,
   `git status|diff|log|show|blame`, `wc`, `sed -n`, временные скрипты в `/tmp`.
5. Каждый RUN пишется в лог Цеха (`--- RUN: …` и код выхода).
6. `CI:` реализует сам исполнитель запросом к GitHub API с токеном из своего окружения (модель токена не видит): список заданий
   запуска → для упавших — конец лога (до 6000 символов). Только чтение.
7. В промпт исполнителя добавь правило: «Упал тест или проверка — сначала разберись: RUN нужной проверки, прочитай вывод,
   найди причину, потом правь. Не гадай».

Тесты части A (это инструмент Цеха, а не сервер — положи их в `tests/hq-agent.test.js`, запуск `node --test tests/hq-agent.test.js`,
добавь его в `check.yml` в задание `server` или отдельным коротким заданием, и в карту влияния `tests/impact.js` для `tools/hq-*`):
- запрещённые команды отклоняются (по одной на каждое правило п. 3);
- в окружении RUN нет секретов;
- таймаут срабатывает (команда `sleep` с маленьким таймаутом через переменную окружения теста);
- вывод обрезается.

## Часть B. Эпики с главным инженером

### B1. Данные (`hqnodes`, тип `epic`)
```
{ id, type:'epic', title, text (цель словами владельца), status, at,
  plan: { summary, architecture, tasks:[ {key, title, what, where, done[], not[], kind, level, core:bool, deps:[key], test} ], risks[], questions[] },
  budgetRub, spentRub, replans, log:[{at, text}] }
```
Задачи эпика — обычные узлы `task` с полями `epic` (id эпика), `ekey` (key из плана), `deps` (id задач-предшественников).

Статусы эпика (и только такие переходы):
```
draft → planning → review(ждёт владельца) → running → done
                       ↘ draft (переплан по замечанию)     running → paused (провал / бюджет / вопрос) → running | failed
```

### B2. Как появляется эпик
- Секретарь: новый intent `epic` — «владелец описывает большую цель, которая потребует многих задач (новая функция, раздел, система)».
  Сомнение между `thoughts` и `epic` → `thoughts` (Аналитик), и в ленте кнопка «Сделать эпиком».
- Кнопка «Сделать эпиком» на любой цели/задаче карты.

### B3. План (Главный инженер, в Цехе — ему нужен код)
Задание `plan` в `hq-work.yml` по метке `эпик` на Issue (Issue создаёт сервер: цель + контекст, без монолога владельца).
Алгоритм:
1. Разведчик (Haiku, команды GREP/READ/NOTE/PACK, как в бригаде) собирает пакет: где в коде то, что затронет цель; похожие
   существующие функции; как устроены тесты рядом. До 1200 строк в пакете.
2. Главный инженер (роль `chief`, по умолчанию Opus, `effort: high`) получает цель + пакет + `docs/ARCHITECTURE.md` + `tests/README.md`
   (только оглавление — первые 60 строк) и пишет план **строго в JSON по схеме B1** (промпт — §B7).
3. Сервер-валидатор плана (функция `validatePlan` в `server/lib/hq/epic.js`, с тестами) отклоняет план, если:
   задач < 3 или > 30; есть цикл в `deps` или ссылка на несуществующий key; у задачи нет `done` или `test`;
   доля `level:'complex'` + `core:true` > 30 %; задача без `where`. При отклонении — один повтор Главному инженеру с текстом
   ошибок; второй провал → эпик `paused`, вопрос владельцу.
4. Оценка цены: сумма `estimate()` по штату для каждой задачи × 1,5 = предложенный `budgetRub`.
5. Результат — комментарий в Issue с JSON между `<!-- hq-plan -->` … `<!-- /hq-plan -->`; сервер забирает при синхронизации.

### B4. Утверждение
В ленте — карточка эпика: цель, архитектура (3–6 строк), список задач с исполнителями и порядком, вопросы Главного
инженера, итоговая оценка. Кнопки: «✅ Утвердить», «✏️ Переплан» (поле замечания → снова B3 с замечанием), «Отменить».
Во вкладке «Задачи» — эпик отдельной дорожкой с прогрессом `сделано / всего`.

### B5. Выполнение (планировщик)
Функция `epicTick()` в `server/lib/hq/epic.js`. Вызывается: из `POST /api/hq/sync` и **из таймера сервера** — функция
`remind()` в `server/lib/app.js` уже запускается каждые 15 минут (`server/index.js`, `exports.remind`): добавь туда вызов
`hq.tick()`, чтобы эпик шёл, даже когда ЛК закрыт.
Алгоритм одного тика, для каждого эпика в `running`:
1. Если `spentRub ≥ budgetRub` → `paused`, запись в ленту «бюджет эпика исчерпан» + кнопки «Добавить 50 %», «Остановить».
2. Если есть задача эпика в `running` → ничего не делать (задачи эпика идут **по одной**: меньше конфликтов, каждая
   опирается на влитую предыдущую).
3. Иначе взять первую по порядку плана задачу в `new`/`ready`, у которой все `deps` в `done`. Нет такой и все в `done` → B6.
4. Перед запуском дописать в её ТЗ блок «Эпик: цель и архитектура (кратко) + что уже сделано (заголовки и по строке из
   отчётов выполненных задач)». Исполнитель — по штату (`STAFF[kind][level]`); `core:true` → роль `chief`.
5. Запустить через существующий путь `run` (Issue «цех», автовыкатка по настройкам).
6. Задача эпика в `failed` → разбор Главным инженером (§B7, второй промпт) по: ТЗ, логу попыток (конец), отчёту Ревизора.
   Его решение (JSON): `retry` (уточнённое ТЗ, тот же или указанный исполнитель) | `split` (2–3 новые задачи вместо этой,
   deps сохраняются) | `reorder` | `ask` (вопрос владельцу → эпик `paused`). Лимиты: ≤ 2 разбора на задачу, ≤ 5 на эпик;
   сверх лимита → `paused` и вопрос владельцу.
7. Задача эпика откачена (`rolled`) → то же, что провал.

### B6. Приёмка эпика
Все задачи `done` → запустить полную проверку main (`gh workflow run check.yml` делает Цех после слияний; дождаться
зелёной последней) → Главный инженер коротко сверяет критерии цели (по отчётам задач, без чтения всего кода) → эпик `done`,
в ленте итог: что сделано, сколько стоило, ссылки на PR. Красная проверка → задача «Починить main» внутри эпика.

### B7. Промпты (положи в `prompts.js` дословно, правь только при явной ошибке)

`CHIEF_PLAN`:
```

без сборки, модули window.ИМЯ; кабинет lk/; облачные функции server/; проверки tests/run.js по блокам, карта влияния tests/impact.js).

Правила плана:

   core: true — только сердце системы, где ошибка ломает всё (обычно 1–3 задачи на эпик). Не завышай: дешёвые исполнители

7. Если без ответа владельца план неоднозначен — вопросы в questions (до 3), а план — для самого вероятного ответа.
Ответь ТОЛЬКО JSON: {"summary":"…","architecture":"…","tasks":[{"key":"t1","title":"…","what":"…","where":"…","done":["…"],"not":["…"],
```

### B8. Тесты части B (`server/test/hq.test.js`, поддельные ProxyAPI и GitHub, как в существующих тестах)

5. В ТЗ задачи есть блок «Эпик: … что уже сделано».
6. `core:true` → исполнитель роли `chief`.

9. Все `done` → приёмка → эпик `done`, итог в ленте.

## Часть C. Сеанс с Opus в ЛК

Цель: владелец общается с исполнителем в ЛК так же, как в Claude Code: говорит — тот делает, показывает, спрашивает.

1. **Запуск.** Кнопка «Сеанс» в ЛК (или Секретарь: intent `session` — «давай поработаем вместе / сеанс»). Сервер создаёт Issue
   с меткой `сеанс` (заголовок — первая фраза), исполнитель по умолчанию — роль `chief`, можно выбрать любого.
2. **Задание `session` в `hq-work.yml`**: `timeout-minutes: 330`, своя очередь по номеру Issue. Цикл в `tools/hq-agent.js --session`:
   - ждёт новых комментариев владельца «💬 Владелец: …» (опрос GitHub раз в 8 с); 20 минут тишины → итоговое сообщение и выход;
   - на каждую реплику — ход агента с командами GREP, READ, EDIT, RUN, CHECK, SHOT, CI, `ASK: вопрос` (спросить владельца и ждать),
     `SAY: текст` (ответить владельцу и ждать следующей реплики), `PR: заголовок` (закоммитить в ветку `hq/session-N`, открыть или
     обновить PR токеном владельца), `MERGE` (только если владелец в этом сеансе написал «влей» и проверка PR зелёная);
   - ответы владельцу — комментарии с маркером `<!-- hq-say -->` и стоимостью хода `<!-- hq:{"rub":…} -->`.
3. **Экономия в сеансе** (обязательно):
   - Claude — через `/v1/messages` с кэшем (как сейчас), системный промпт + карта проекта — в кэше;
   - поиск и чтение больших кусков — делегировать: команда `SCOUT: что найти` → Haiku-разведчик возвращает пакет (как в бригаде);
   - история > 120 тыс. токенов → сжать: старые ходы заменяются сводкой от Haiku (что сделано, решения, открытые вопросы);
   - в ленте после каждого хода — стоимость хода и сеанса; потолок сеанса (по умолчанию 300 ₽, в «Сотрудниках») → пауза и вопрос.
4. **ЛК: вкладка «Сеанс»** — чат, привязанный к Issue сеанса: сообщения владельца уходят комментарием (как реплики), ответы
   подтягиваются опросом `GET /api/hq/session?id=` раз в 5 с, пока вкладка открыта; кнопки «Влей», «Стоп», ссылки на PR.
5. Тесты: сервер (создание сеанса, реплика → комментарий, ответ → лента, потолок), исполнитель (`--session` на поддельном
   ProxyAPI и поддельном GitHub: реплика → GREP → SAY; «влей» без зелёной проверки → отказ; сжатие истории при пороге).

## Часть D. Живая приёмка

После слияния A–C, по одному, с отчётом владельцу в ленте и в чате:
1. **Эпик-проба** на пульте владельца `me/` (студенты его не видят): «Добавить в пульт панель «Здоровье сайта»: последние 5 запусков
   проверки main (зелёный/красный), открытые Issue «main-красный», кнопка открыть лог». Ожидается 3–5 задач, Opus — только план.
2. **Сеанс-проба**: 10 минут живого диалога о коде (вопрос → ответ со строками → маленькая правка → PR → «влей»).
3. В отчёте: сколько задач, кто их делал, сколько стоил каждый шаг, где Opus, что сломалось и как починено.

Только после этого — эпик «ИИ-ассистент на чертеже» (его формулирует владелец).

## Правила работы для агента-разработчика

- Без новых зависимостей (сервер и инструменты — чистый Node 20+, как сейчас). `index.html` сайта в этом задании не трогать.
- Тексты интерфейса — по-русски, коротко, на «ты».
- Перед каждым пушем: `cd server && npm test`, `node --check` изменённых файлов, `bash -n` всех `run:` изменённых workflow
  (скрипт: разобрать YAML, каждый `run` → `bash -n`), карта влияния `node tests/impact.js origin/main`.
- Каждая часть — PR с описанием «что / почему / как проверено». Проверка зелёная → можно вливать (владелец разрешил).
- После слияния части с серверным кодом — развёртывание: Actions → «Личный кабинет — развёртывание в Yandex Cloud» (`club.yml`)
  с main. Новые таблицы не нужны (эпики и сеансы — в `hqnodes`, лента — `hqfeed`).
- Нашёл ошибку в существующем коде Штаба — чини в той же части, напиши об этом в PR.
- Не уверен в поведении внешнего сервиса (ProxyAPI, GitHub) — проверь живым маленьким запросом через Цех, а не гаданием.
